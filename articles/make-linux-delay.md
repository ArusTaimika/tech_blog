# 🌐 概要

## 🧩 課題

ネットワークを利用するシステムを開発する際，通信遅延やパケットロスが発生した場合の動作を検証したいことがある．
しかし，実際のネットワークで通信品質の悪化を再現するには，環境の準備や条件の統一が難しい．
例えば，以下のようなケースが考えられる．
- 遠隔地との通信を想定した遅延の再現
- 通信が不安定な環境での動作確認
- 通信遅延が制御性能に与える影響の評価
- パケットロスが発生した場合のエラー処理の検証

## 💡 結論

Linuxの `tc` コマンドと `netem` を使用することで，ネットワーク遅延やパケットロスなどを意図的に発生させることができる．
```bash
# 200 msの遅延を追加
sudo tc qdisc add dev eth0 root netem delay 200ms
# 設定を解除
sudo tc qdisc del dev eth0 root
```

`eth0` はネットワークインターフェース名の例である．実際の環境に合わせて変更する．

# 🎯 背景・目的

## 💭 なぜネットワーク遅延を再現するのか？

- ネットワークを利用するシステムは，通信環境によって動作が変化する．
- 例えば，ローカルネットワークでは問題なく動作するシステムでも，通信遅延が大きくなると応答が遅れたり，期待したタイミングで処理が実行されなかったりする可能性がある．
- こうした問題を事前に検証する方法の一つが，**ネットワークエミュレーション** である．通信遅延やパケットロスを意図的に発生させることで，実際の通信環境が悪化した場合の動作を確認できる．

## 🛠️ tc・netemとは？

- Linuxでは，`tc`（Traffic Control）コマンドを使用して，ネットワークインターフェースの送信トラフィックを制御できる．
- その機能の一つである `netem`（Network Emulator）を利用すると，以下のような通信条件を再現できる．

  - ⏱️ **遅延・ジッタ**：通信の遅れやばらつき
  - 📉 **パケットロス**：パケットの欠落
  - 🔁 **パケット複製・破損**：重複や破損が発生する通信環境

## 🚀 主な活用例

| 活用分野 | 検証内容 |
| --- | --- |
| 🤖 遠隔操作ロボット | 通信遅延が位置・力の追従性能に与える影響 |
| 🌐 Webアプリケーション | APIの応答遅延やタイムアウト処理 |
| 🖥️ 分散システム | 通信障害時の再試行やデータ同期 |
| 📡 通信システム | 遅延変動やパケットロスに対する耐性 |

この記事では，`tc` と `netem` の基本的な設定方法を整理し，通信品質を変化させる方法を紹介する．

# 🛠️ 手順・苦戦ポイント
## 1. ネットワークインターフェースの確認

最初に，設定対象のネットワークインターフェースを確認する．

```bash
ip link show
```

表示されたインターフェースのうち，使用するものを選択する．例えば，`eth0` や `wlan0` などがある．
以降のコマンドでは，`eth0` を使用する．

## 2. ネットワーク遅延の設定

### Step 1：一定の遅延を追加する

`delay` を使用すると，パケットに一定の遅延を追加できる．

```bash
sudo tc qdisc add dev eth0 root netem delay 200ms
```

この設定では，`eth0` から送信されるパケットに約200 msの遅延を追加する．
なお，これは指定したインターフェースの送信方向に対する設定であり，通信の往復遅延（RTT）が必ず200 msになるわけではない．

### Step 2：ジッタを追加する

実際のネットワークでは，通信遅延が一定ではなく，時間によって変動する場合がある．このような遅延のばらつきは，ジッタと呼ばれる．

```bash
sudo tc qdisc add dev eth0 root netem delay 200ms 20ms distribution normal
```

200 msを基準として，標準偏差20 msの正規分布に従う遅延変動を指定する．
モバイルネットワークなど，遅延が変動する環境を模擬する際に利用できる．

### Step 3：パケットロスを発生させる

`loss` を使用すると，一定の確率でパケットを破棄できる．

```bash
sudo tc qdisc add dev eth0 root netem loss 10%
```

この設定では，パケットロス率を10%に設定する．
通信相手にデータが届かなかった場合の再送処理やタイムアウト処理などを検証できる．

### Step 4：その他の通信条件を設定する

`netem` では，遅延やパケットロス以外にも，パケットの複製や破損を設定できる．

| 設定 | コマンド例 | 内容 |
| --- | --- | --- |
| パケット複製 | `duplicate 2%` | 2%の確率でパケットを複製する |
| パケット破損 | `corrupt 0.1%` | 0.1%の確率でパケットの破損を発生させる |

例えば，パケットの複製を設定する場合は，以下のようにする．

```bash
sudo tc qdisc add dev eth0 root netem duplicate 2%
```

各設定は独立した例である．すでに `root` にqdiscを設定している場合は，同じコマンドを続けて実行するのではなく，`change` などを使用して設定を変更する．

## 3. 設定の確認と解除

### Step 1：現在の設定を確認する

```bash
sudo tc qdisc show dev eth0
```

設定した遅延やパケットロスなどが反映されているかを確認する．

### Step 2：設定を解除する

```bash
sudo tc qdisc del dev eth0 root
```

設定が不要になったら，qdiscを削除して元の状態に戻す．
なお，既存のqdisc設定がある環境では，削除によってほかの設定にも影響する可能性があるため注意する．

## 4. 苦戦ポイント

### ⚠️ OSI参照モデルのどの層に影響するのか？

- `tc` はLinuxカーネルのネットワーク制御機能であり，OSI参照モデルの特定の1層だけに対応するものではない．
- `netem` はパケットの送信キューに遅延やパケットロスなどを設定する機能である．
- 通信全体の遅延には，`netem` による遅延だけでなく，各層の処理時間も影響する．
  - **アプリケーション層（第7層）：** データの生成・処理，送信処理の待ち時間
  - **トランスポート層（第4層）：** TCPの再送，輻輳制御など
  - **ネットワーク層（第3層）：** IPパケットの転送やルーティング
  - **データリンク層（第2層）：** フレームの送信やキューでの待ち時間
- 各処理の重なりやTCPの再送などによって遅延は変化するため，`netem` の設定値だけで通信全体の遅延が決まるわけではない．

### ⚠️ 設定がほかの通信にも影響する

- `netem` をインターフェース全体に設定すると，対象のアプリケーション以外の送信通信にも影響する場合がある．
- SSHで接続している環境では，通信遅延やパケットロスによって操作が困難になったり，接続が切断されたりする可能性がある．
- 設定前に，接続が切れた場合の復旧手段を確保しておくことが重要である．

### ⚠️ 往復通信の遅延を評価する際の注意点

- `netem` の設定は，基本的に指定したネットワークインターフェースの送信方向に適用される．
- PCからロボットへの通信に200 msの遅延を設定しても，ロボットからPCへの通信に同じ遅延が直接適用されるわけではない．
- `ping` などで測定する往復遅延（RTT）には，設定した遅延に加え，復路の通信遅延なども含まれる．
- **往復通信全体の遅延を評価する場合は，往路と復路の両方に遅延を設定する必要があるかを検討する．**
- 片方向の遅延だけを設定した場合，測定したRTTをそのまま片方向の通信遅延として扱わないように注意する．



# 📝 まとめ

今回は，Linuxの `tc` コマンドと `netem` を使用して，ネットワーク遅延やパケットロスを再現する方法を整理した．
主なコマンドは以下のとおりである．

| 機能 | 設定例 |
| --- | --- |
| 遅延 | `delay 200ms` |
| ジッタ | `delay 200ms 20ms distribution normal` |
| パケットロス | `loss 10%` |
| パケット複製 | `duplicate 2%` |
| パケット破損 | `corrupt 0.1%` |

ネットワーク遅延を意図的に発生させることで，実際の通信環境を用意しなくても，通信品質の変化に対するシステムの挙動を検証できる．
今後は，設定した遅延と実際の通信遅延を比較したり，複数の通信条件でシステムの応答性を評価したりすることで，より実践的な検証に活用できる．
